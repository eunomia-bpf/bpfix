# Semantic Preservation

Verifier acceptance is only one repair condition. Before editing, write a
compact contract from source, loader, tests, and surrounding code.

## Contract Checklist

- Keep loader-visible program names, sections, map definitions, and return
  actions unless the verifier evidence proves that one of them is the bug.
- Record each map operation with its key source, value source, mutation, and
  ordering. Do not substitute packet/context data for a value intentionally
  loaded from another map.
- Record externally visible side effects: map updates/deletes, counters,
  ringbuf/perf events and fields, redirects, tail calls, and resource release.
- Record branch behavior for valid, short/malformed, lookup-miss, allocation-
  failure, and ordinary nonmatching inputs.
- Preserve meaningful source-level dataflow as well as runtime outputs when the
  project tests or generated bytecode rely on aliases, helper argument origins,
  lookup counts, or operation order. Prefer deleting one bad arithmetic or
  overwrite operation over folding the entire surrounding path.
- Identify fallback values. A nullable override lookup often means "keep the
  proven default on miss," not "return early on miss."
- For acquired resources, record acquisition order and the required terminal
  action for every later failure path. A new allocation can require cleanup of
  an earlier successful allocation.

Summarize this as invariants before choosing a rewrite:

```text
must keep: <dataflow, side effects, branch results, protocol operations>
may change: <the local proof-establishment or proof-loss relation>
must not substitute: <lookalike value with different semantic origin>
```

## Common Semantic Traps

- A verifier-safe early return can silently remove fallback policy, state
  cleanup, event emission, or a later map update.
- Clamping a length or masking an index changes behavior unless wrapping or
  truncation is part of the original contract. Prefer a rejecting guard when
  invalid input should not be processed.
- Repeating a lookup can change which value is observed and can reintroduce
  nullability. Preserve a proven pointer or store a nullable override in a
  separate temporary.
- Replacing a helper operation with direct packet access can bypass the API or
  protocol behavior the program is intended to exercise.
- Deleting a bad helper call is not a repair when its side effect is required.
  Supply the correct pointer, context, size, section, or lifecycle instead.
- Returning a constant verifier-friendly action is never evidence that packet
  parsing, policy lookup, and state updates were preserved.

## Validate The Contract

Rebuild and load first, then exercise at least one input for each meaningful
branch. Inspect map/event side effects as well as return values. When tests are
unavailable, compare the candidate's helper/map operations and dataflow with
the original source and state which semantic behavior remains untested.
